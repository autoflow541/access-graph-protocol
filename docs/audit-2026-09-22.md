# Implementation audit and pilot plan — 22 September 2026

Baseline: `df8b8ba`, package 0.1.9. Review scope: JavaScript core, WoT/ARIA adapters, SPECS action session, tests, and roadmap. This is an engineering review, not security certification. No Lens Studio compilation, headset verification, physical device tests, or participant sessions were performed.

## Verdict

A useful experimental SDK with simulated workflows. Not yet a deployed accessibility service, verified SPECS application, or production device controller. Six existing suites passed at baseline; those suites did not catch the recursive constraint defect below.

## Behavior and compatibility

The session validates AGP's current typed parameter subset, including nested requiredness, numeric bounds and enum choices. It rejects undeclared input fields, nonempty arrays without item schemas, and unsupported types. This is stricter than prior behavior and is not a full JSON Schema validator. Objects are closed in this reference session; open-ended objects require an explicit future design. Unknown properties must not be silently forwarded.

Expiry is **opt-in** so existing clients do not unexpectedly time out without an accessible recovery flow:

```js
const session = new SpecsActionSession(graph, profile, executor, {
  proposalTtlMs: 120_000
});
```

Handle errors with `code === "PROPOSAL_EXPIRED"` by explaining that approval expired and offering a fresh review. Cancellation remains available. Never silently renew approval. Accommodate users who need more time; select lifetimes from device policy and offer re-proposal without requiring unnecessary re-entry. The clock is local convenience, not a security boundary; a future server must own authoritative expiry.

The `sensitive: true` parameter annotation hides a **whole top-level field** from the confirmation text. It is not encryption, automatic secret detection, or recursive redaction. Integrators must annotate sensitive fields and avoid logging parameters. Adapters do not automatically infer this flag. Any nested sensitive content should have its top-level container marked sensitive.

## Features worth building next, in order

1. **Authoritative execution service.** Scoped authenticated requests, reviewed device/action allowlist, proposal IDs, parameter digest, state version, expiry and duplicate-request handling. Test rejection before dispatch and uncertain outcomes after timeout. Acceptance: spoofed client authorization never dispatches; repeating one request ID never triggers a second dispatch during the documented retention window. Define restart persistence before claiming replay safety across restarts.
2. **Live state and connection health.** Show observed time, stale/unknown values, offline status and reconnect behavior. Acceptance: disconnect a simulator and neither client displays old data as current; reconnect reconciles state without replaying commands.
3. **Accessible task inspector.** Keyboard-operable view of available actions, parameters, risk, policy provenance, and an explanation of why an action is blocked. Acceptance: browser screen-reader and keyboard checks of a complete task including denial/recovery.
4. **Client capability negotiation.** Compare required access needs with available input/output, explain conflicts, offer alternatives, and allow user override. Never infer a diagnosis from a preference.
5. **Scenario runner.** Reproducible simulator faults: timeout, denial, state change, duplicate request, malformed schema. Produce a machine-readable pass/fail report; treat it as implementation testing, not accessibility certification.
6. **Real pilot integration.** One real lamp through a supported device backend, browser first, SPECS second. Heating, locks and motion remain simulated until device-specific safeguards are reviewed.

These priorities follow observed repository gaps and existing research in `docs/prior-art-and-positioning.md`; they are proposals, not customer-demand evidence.

## Criteria for calling this a pilot-ready product

- Real client/service boundary and server-side permission enforcement.
- Reproducible installation with pinned dependencies and CI on supported runtimes.
- Documented supported schema/transport subset, protocol versus package versions, and error contract.
- Observed state, accepted command and completed effect are distinguished.
- One external developer completes an integration from the documentation.
- Browser workflow evaluated using keyboard and an actual screen reader.
- Lens compilation and hardware test record with exact versions before claiming SPECS compatibility.
- Paid formative sessions with relevant disabled participants; report errors, effort, fatigue, and negative findings.
- A customer agrees to a narrow pilot with measurable outcomes and support responsibilities.

## Commercial focus

Interview potential workplace/training or accessible room-control buyers while building the execution service. Sell integration, tested task completion, and support. Keep the protocol open. Avoid claiming universal accessibility, standards approval, or automatic compliance. A successful pilot and independent implementation are stronger evidence than another adapter or more branding.

## Verification

`npm test` runs the original six suites plus the new proposal validation suite. New checks exercise bounds and enums in nested objects and arrays, unknown fields, requiredness, wrong types, input mutation, key-order-independent comparison, confirmation previews, explicit redaction, expiry at each advancing transition, cancellation, recovery and no dispatch on expiration. No claim is made about on-device behavior from these Node tests.
