# Implementation audit and pilot plan: 22 September 2026

Baseline: `df8b8ba`, package 0.1.9. Review scope: JavaScript core, WoT/ARIA adapters, SPECS action session, tests, and roadmap. This is an engineering review, not security certification. No Lens Studio compilation, headset verification, physical device tests, or participant sessions were performed.

## Verdict

A useful experimental SDK with simulated workflows. Not yet a deployed accessibility service, verified SPECS application, or production device controller. Six existing suites passed at baseline; those suites did not catch the recursive constraint defect below.

## Behavior and compatibility

The session validates AGP's current typed parameter subset, including nested requiredness, numeric bounds and enum choices. It rejects undeclared input fields, nonempty arrays without item schemas, and unsupported types. This is stricter than prior behavior and is not a full JSON Schema validator. Objects are closed in this reference session; open-ended objects require an explicit future design. Unknown properties must not be silently forwarded.

Expiry is **opt-in** so existing clients do not unexpectedly time out without an accessible recovery flow:

```js
const session = new SpecsActionSession(graph, profile, executor, {
  proposalTtlMs: 120_000
});
```

Handle errors with `code === "PROPOSAL_EXPIRED"` by explaining that approval expired and offering a fresh review. Cancellation remains available. Never silently renew approval. Accommodate users who need more time; select lifetimes from device policy and offer re-proposal without requiring unnecessary re-entry. The clock is local convenience, not a security boundary; a future server must own authoritative expiry.

The `sensitive: true` parameter annotation hides a **whole top-level field** from the confirmation text. It is not encryption, automatic secret detection, or recursive redaction. Integrators must annotate sensitive fields and avoid logging parameters. Adapters do not automatically infer this flag. Any nested sensitive content should have its top-level container marked sensitive.

## Features worth building next, in order

1. **Authoritative execution service.** Started: `service/execution-service.js` and `service/http-server.js`: scoped authenticated requests, the reviewed device/action allowlist (the `AccessGraph` passed to the constructor *is* the allowlist), proposal IDs, state version, proposal expiry, and duplicate-request handling are implemented and tested, in-process and over real HTTP (`tests/execution-service-test.mjs`, `tests/execution-http-server-test.mjs`). Rejection before dispatch and an "unknown" outcome after a dispatch timeout are both tested. Acceptance verified: a spoofed/unauthenticated caller never reaches dispatch (asserted via executor call count); repeating one request ID never triggers a second dispatch within the documented retention window. Restart persistence is explicitly NOT claimed: state is in-memory only; see `service/README.md`, "What's not done yet." Authorization itself remains simulated by default (now a pluggable `authorizationProvider`, not a solved backend): do not read this item as closed.
2. **Live state and connection health.** Show observed time, stale/unknown values, offline status and reconnect behavior. Acceptance: disconnect a simulator and neither client displays old data as current; reconnect reconciles state without replaying commands.
3. **Accessible task inspector.** Started: `ExecutionService.inspect()` (`service/execution-service.js`) returns every declared action's server-resolved confirmation/authorization verdict (via `AccessGraph.resolveAction`, folding in the Access Profile: not just the action's own declared flags), its category-trust provenance (`metadata.category_trust`: "reviewed" vs "declared", from the WoT adapter's category-trust fix), and a structural blocked reason where one exists (currently: an unsupported parameter schema: the one block condition this codebase can determine without side effects; it does not model state-dependent "not applicable right now" blocking, since nothing computes that yet). Exposed over HTTP as `GET /devices/:id/inspect` and tested in-process and over real HTTP (`tests/execution-service-test.mjs`, `tests/execution-http-server-test.mjs`), including that a category-only confirmation trigger is correctly surfaced even when the action's own `confirmation` flag is `false`. Rendered in `examples/execution-client/` as a native `<details>`/`<summary>` disclosure per action: zero custom JS for the disclosure interaction itself, matching the WAI-ARIA APG disclosure pattern. Verified live: mouse activation opens each entry and shows correct, server-computed content (checked against a curl of the same endpoint); `Tab` moves focus through every entry. **Not verified**: synthetic `Enter`/`Space` key activation through the browser-automation tool used for this check did not toggle the disclosure: reproduced identically on the page's pre-existing, previously-accepted `<details>` block, so this reads as a limitation of that automation tool's key-event dispatch against native UA default actions, not a defect in the markup (native `<summary>` keyboard activation requires no code and is universally supported by real browsers). No real screen reader has been used against this or any other browser example in this repo: see "Criteria," below. Do not read this item as fully closed on the acceptance criterion as written.
4. **Client capability negotiation.** Started: `negotiateCapabilities(object, clientCapabilities)` (`sdk/javascript/agp.js`) compares an object's declared `inputs`/`outputs` against what the *current client session* reports it can provide, and returns `canControl`/`canPerceive`, which channels are supported vs missing, and a plain-language explanation per gap: naming a working alternative when one exists ("can still be controlled here via touch"), and saying so plainly when none does ("No alternative input is available in this session"), never inventing one. It takes no `profile` argument at all (asserted by an arity check in the test, not just a comment): a client not reporting "voice" is a technical fact about this session, never evidence about the person, so it can't structurally be read as one. It only ever informs: nothing it returns disables or hides an action, so the user-override requirement holds by construction, not by a caller remembering not to gate on it. Tested (`tests/capability-negotiation-test.mjs`): full match, partial match with a named alternative, full mismatch with no invented alternative, mirrored for both inputs and outputs, plus the empty-object and omitted-clientCapabilities edge cases. Rendered live in `examples/execution-client/` as a "Client capability negotiation" panel: four checkboxes (touch/voice inputs, visual/audio outputs) the person can toggle to simulate a session without that channel, computed client-side (this is the one thing in that page NOT fetched from the service, since only the client can know its own session's channels). The demo thermostat (`service/run-local.mjs`) now declares realistic `x-agp-inputs: ["touch","voice"]` / `x-agp-outputs: ["visual","audio"]` so there's something real to negotiate against. Verified live: unchecking "Voice input" produces "Hall thermostat also accepts voice, which this session doesn't report as available. It can still be controlled here via network, touch."; unchecking "Visual output" produces the mirrored output-side explanation; every action button (including "Emergency shutdown") stays enabled throughout, confirmed via the accessibility tree, not just visually. Not done: this is object-level only (matching the existing `inputs`/`outputs` schema fields), not per-action; there is no UI anywhere that reads a *real* device/browser's actual capabilities (e.g. `navigator` feature detection, a paired AT's reported modalities): the checkboxes are a manual simulation, not live capability detection.
5. **Scenario runner.** Reproducible simulator faults: timeout, denial, state change, duplicate request, malformed schema. Produce a machine-readable pass/fail report; treat it as implementation testing, not accessibility certification.
6. **Real pilot integration.** One real lamp through a supported device backend, browser first, SPECS second. Heating, locks and motion remain simulated until device-specific safeguards are reviewed. Partially started: `service/wot-executor.mjs` dispatches through a real `node-wot` `ConsumedThing` (see `docs/adr-0001-wot-reuse.md` point 4 and `ROADMAP.md`'s M2), but `service/virtual-thermostat.mjs` is still simulated hardware behind that real protocol stack, not a physical lamp. This item stays open until that's a real device.

These priorities follow observed repository gaps and existing research in `docs/prior-art-and-positioning.md`; they are proposals, not customer-demand evidence.

## Criteria for calling this a pilot-ready product

- Real client/service boundary and server-side permission enforcement.
- Reproducible installation with pinned dependencies and CI on supported runtimes.
- Documented supported schema/transport subset, protocol versus package versions, and error contract.
- Observed state, accepted command and completed effect are distinguished.
- One external developer completes an integration from the documentation.
- Browser workflow evaluated using keyboard and an actual screen reader.
- Lens compilation and hardware test record with exact versions before claiming SPECS compatibility.
- Paid formative sessions with relevant disabled participants; report errors, effort, fatigue, and negative findings.
- A customer agrees to a narrow pilot with measurable outcomes and support responsibilities.

## Commercial focus

Interview potential workplace/training or accessible room-control buyers while building the execution service. Sell integration, tested task completion, and support. Keep the protocol open. Avoid claiming universal accessibility, standards approval, or automatic compliance. A successful pilot and independent implementation are stronger evidence than another adapter or more branding.
