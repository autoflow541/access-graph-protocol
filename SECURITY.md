# Security

AGP may describe actions that affect physical devices, accounts, finances, security systems, or other consequential systems.

The current prototype is **not** a security boundary. Implementations must preserve the underlying platform's authentication, authorization, safety interlocks, rate limits, and audit controls.

Do not treat an Access Profile as permission to perform an action. Do not allow accessibility adaptation to weaken authorization requirements.

Do not treat recognized speech, gaze, hand tracking, a switch event, an AI-generated intent, or possession of an XR device as authentication or authorization. Platform adapters must keep confirmation and authorization as separate gates and must delegate actual permission checks to the underlying service.

The WoT adapter never invokes forms or accepts credentials. Its default classification for unknown writes and device actions is medium risk with confirmation required. Implementers should replace that default only from trusted, explicit device metadata or a reviewed policy.

For the `physical_safety`, `security`, `financial`, and `destructive` action categories, the WoT adapter enforces a policy floor (`adapters/wot/index.js`, `CATEGORY_RISK_FLOOR` / `CATEGORY_CONFIRMATION_FLOOR`): a source-declared `x-agp-risk` or `x-agp-confirmation` can raise the effective requirement, but can never lower it below the floor for that category. A device cannot self-declare a physical-safety action as low-risk or no-confirmation. This does not extend to the category label itself: `x-agp-category` remains source-declared, so a device that mislabels a dangerous action as `device_control` currently evades the floor. Closing that requires category classification from a reviewed or allowlisted source rather than the device itself; see `docs/capability-matrix.md` (Finding G) and `ROADMAP.md`.

`adapters/vision-assistant/` (an AI-described-environment capability: "what am I looking at?", "read this to me") introduces a concern AGP's existing risk model was never built for. `risk`/`confirmation` are about the *consequence of an action*; a camera-description request has none (it changes nothing in the world), which is why both its actions are correctly `risk: "none"`. But every request sends one still frame somewhere for description, and that frame can contain other people who never consented to being described, recorded, or (if a real describer logs requests) retained. AGP does not model this today: no field distinguishes "safe to auto-approve" from "captures data about people who aren't the user." Implementers of a real describer are responsible for that: do not log or retain captured frames beyond what completing the request requires, and do not send them anywhere the user has not been told about. This is a real, open gap, not a solved one; see `docs/adr-0001-wot-reuse.md`-style future work. `ANTHROPIC_API_KEY`, when set for a real describer (`service/describers/anthropic-describer.mjs`), stays server-side in `service/run-local-vision.mjs`: it is never sent to or readable from `examples/vision-assistant/`'s browser client. Do not change that; a key shipped to a browser is a leaked key.

`adapters/web-vision/` sends a full screenshot to the configured describer, which can contain private account content, messages, or anything else visible on screen at the moment of capture, same caution as `adapters/vision-assistant/`'s camera frames above.

`adapters/web-scan/` sends a URL to the configured scan backend, which fetches and renders it server-side. Do not scan a URL behind authentication you are not permitted to expose to a third-party service.

`adapters/pdf-remediation/` sends the full PDF to a configured remediation backend (Auto-Flow's pdf.auto-flow.co by default, `AGP_PDF_SERVICE_URL` to point elsewhere). Do not use this on a document you are not permitted to send to that service. `remediate` requires confirmation for exactly this reason, alongside it being an AI-judgment action: a person should see that a document is about to be sent out for processing, not have it happen silently.

`service/wot-executor.mjs` dispatches real WoT actions through `@node-wot/core`/`@node-wot/binding-http`. That dependency tree currently carries moderate/high transitive advisories in its HTTP server's router and query-string parsing (`decode-uri-component`, `find-my-way`); `npm audit` shows the details. No fix is available without downgrading to a much older, less-maintained `node-wot` release. `service/virtual-thermostat.mjs` binds to `127.0.0.1` only and uses `nosec` (no transport-level security), so it is a local development Thing, not something to expose to an untrusted network. Do not point `service/run-local-wot.mjs` at a `node-wot`-exposed Thing reachable from the internet without re-evaluating this.

Fixed 2026-09-23, from a pasted external audit verified against source before acting on it (see `CHANGELOG.md`'s 0.1.25 entry and `tests/security-fixes-test.mjs`):

- All six `service/run-local*.mjs` dev entrypoints used to call `server.listen(port)` with no host, which binds every interface (`::`/`0.0.0.0`), not just localhost: anything else on the same network could reach a dev instance. They now bind `127.0.0.1` explicitly, matching `service/virtual-thermostat.mjs`'s existing default. They also no longer fall back to the literal string `"dev-token"` when `AGP_DEV_TOKEN` is unset: `service/dev-token.mjs` generates a random token per run instead, printed to the console the same way.
- `ExecutionService.confirm()` and `SpecsActionSession.confirm()` (`adapters/specs/index.js`) checked `if (!accepted)`, so a truthy non-boolean (`"false"` the string, `1`, `{}`) read as consent. Both now require the literal `accepted === true`, matching `provideAuthorization()`'s existing, stricter check.
- `ExecutionService.execute()`'s requestId idempotency cache was checked before `_authenticate()` ran, and was keyed by `requestId` alone, shared across every caller. An unauthenticated request for a known `requestId` could return another caller's cached outcome, and two different callers reusing the same `requestId` string could collide. Authentication now runs first, and the cache key is `callerToken:requestId`.
- `AccessGraph.register()` silently overwrote an existing object id, and did not validate an action's `risk` value against `RISK_ORDER`; an unrecognized value's `indexOf()` was `-1`, which read as "less than high" and skipped confirmation, the opposite of what an unrecognized risk should mean. `register()` now rejects a duplicate object id, a duplicate action id within one object, and an unrecognized risk value outright, and `requiresConfirmationFor()` additionally treats an unrecognized risk as requiring confirmation as a fail-conservative backstop for any action object that reaches it some other way.
- `AccessGraph.get()` returned the live internal object, not a clone (inconsistent with `list()` and `resolveAction()`, which already cloned): any caller holding a `get()` result could mutate the real policy graph. `get()` now clones, matching the others; the internal-only `require()` accessor is unchanged and still returns the live reference, since `updateState()` needs to mutate it.
- `service/http-server.js`'s `readJsonBody()` buffered every chunk of a POST body with no size limit, before authentication runs. It now enforces a `maxBodyBytes` constructor option (default 25MB) and returns `413 PAYLOAD_TOO_LARGE` once exceeded, without buffering the oversized remainder.

For the prototype, report security concerns privately to the project maintainer rather than publishing exploit details in a public issue.
